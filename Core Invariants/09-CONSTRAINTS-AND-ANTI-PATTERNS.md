## 0. القيود المؤقتة (Temporary Limitations)

> **ملاحظة:** هذه قيود تقنية مؤقتة، وليست قيود تصميمية دائمة.

### 0.1 تداخل البلوكات المخصصة (Nested Custom Blocks)

**الحالة:** ⏳ غير مدعوم حالياً (مؤجل إلى Phase 2 - Q2 2026)

**الوصف:**
حالياً، النظام لا يدعم تداخل البلوكات المخصصة داخل بعضها البعض.

**أمثلة غير مدعومة:**

```artoon
<alert>.
  <note>.
    >.p:: محتوى متداخل
  .<note>
.<alert>

<container>.
  <card>.
    >.p:: محتوى
  .<card>
.<container>
```

**الحل البديل الحالي:**
استخدم بلوكات بسيطة بدون تداخل:

```artoon
<alert>.
>.p:: هذا تنبيه مهم
.<alert>

<note>.
>.p:: هذه ملاحظة
.<note>
```

**البلوكات المتأثرة:**
- `alert`, `success`, `error`, `warning` - تحتاج تداخل للعمل بشكل كامل
- `article`, `section`, `container` - مصممة للتداخل
- **البلوكات العاملة:** `code`, `meta`, `note`, `info`, `quote`, `card`, `box`, `panel` (8/15) ✅

**خارطة الطريق:**
- **Phase 2 (Q2 2026):** دعم تداخل مستوى واحد
- **Phase 3 (Q3 2026):** دعم تداخل متعدد المستويات

**السبب التقني:**
- Parser يحتاج تحديث لتتبع مستويات التداخل
- AST يحتاج هيكل شجري للبلوكات المتداخلة
- Renderer يحتاج منطق عرض متداخل
- Editor يحتاج واجهة لإدارة التداخل

## 1. القيود المطلقة (Absolute Constraints)

### 1.1 ممنوع: أي معلومة بصرية

```
✗ الألوان          color, background, border-color
✗ الأبعاد          width, height, margin, padding
✗ الخطوط           font-family, font-size, font-weight
✗ التخطيط          grid, flex, columns, float
✗ الموضع           position, top, left, z-index
✗ التحويلات        transform, rotate, scale
✗ الشفافية         opacity, visibility
```

**لماذا؟** ARTOON تجيب عن "ما هو؟" وليس "كيف يبدو؟"

### 1.2 ممنوع: أي سلوك تفاعلي

```
✗ الأحداث          onclick, onhover, onchange
✗ التحريك          animation, transition
✗ التشغيل التلقائي  autoplay, loop
✗ التحقق           validation, required
✗ الحالة           disabled, readonly, checked
```

**لماذا؟** السلوك = طبقة التطبيق، وليس طبقة المحتوى

### 1.3 ممنوع: أي منطق برمجي

```
✗ الشروط           if, else, switch
✗ الحلقات          for, while, each
✗ المتغيرات        $var, {{var}}, {var}
✗ التعبيرات        expressions, calculations
✗ القوالب          templates, includes
```

**لماذا؟** ARTOON ملف محتوى ثابت، وليس لغة برمجة

## 2. الفصل الواضح بين المفاهيم

### 2.1 الكود: سطري vs بلوك

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│   >.c:: code                    ← كود سطري داخل نص (inline)            │
│                                    يُستخدم داخل فقرة أو عنوان          │
│                                                                         │
│   <code:lang>.                  ← بلوك كود متعدد الأسطر                │
│   ...                              مستقل، له بداية ونهاية صريحة        │
│   .<code>                                                               │
│                                                                         │
│   ✗ ممنوع: >.c{} أو أي صيغة أخرى                                       │
│   ✗ ممنوع: خلط الاستخدامين                                             │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.2 العناوين t1-t6: دلالة بنيوية وليست بصرية

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│   t1-t6 = هرمية المعنى (Semantic Hierarchy)                            │
│                                                                         │
│   ✓ t1 = الموضوع الرئيسي للمستند                                       │
│   ✓ t2 = قسم رئيسي                                                     │
│   ✓ t3 = قسم فرعي                                                      │
│   ✓ t4-t6 = مستويات أعمق                                               │
│                                                                         │
│   ✗ ليست "حجم الخط"                                                    │
│   ✗ ليست "شكل العنوان"                                                 │
│   ✗ ليست انعكاساً لـ HTML                                              │
│                                                                         │
│   المبرر: بنية المستند تحتاج تسلسلاً هرمياً للمعنى                     │
│   مثل: كتاب > فصل > قسم > فقرة                                         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 3. حدود المكونات المركبة (Compound Components)

### 3.1 Core يحتوي فقط:

```
✓ figure    ← شكل مع تعليق (صورة/فيديو + caption)
✓ details   ← محتوى قابل للطي (summary + content)
```

### 3.2 لماذا هذان فقط؟

| المكون | المبرر الدلالي |
|--------|----------------|
| `figure` | علاقة دلالية أصيلة: الوسيط + وصفه |
| `details` | علاقة دلالية أصيلة: العنوان + التفاصيل |

### 3.3 ممنوع في Core:

```
✗ card, hero, banner         ← أنماط UI وليست دلالات
✗ tabs, accordion, carousel  ← سلوك تفاعلي
✗ modal, popup, tooltip      ← طبقة العرض
✗ navbar, sidebar, footer    ← تخطيط الصفحة
✗ form, input, button        ← عناصر تفاعلية
```

### 3.4 البديل:

```
أي pattern آخر = Block مخصص خارج Core

<card>.
>.img:: photo.jpg
>.t3:: العنوان
>.p:: الوصف
.<card>
```

## 4. قواعد التضمين الداخلي (Inline Integration)

### 4.1 القاعدة الذهبية

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│   التصريح الداخلي لا يُنشئ بنية                                        │
│   التصريح البنيوي فقط هو الذي يُنشئ كيانًا                             │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.2 مسموح داخلياً (واصفات دلالية):

```
✓ a, img, audio, video, file    ← روابط ومراجع
✓ abbr, time                    ← دلالات
✓ c                             ← كود سطري
✓ s, e, u, d, mark, sub, sup    ← متحكمات نصية
```

### 4.3 ممنوع داخلياً (بنى):

```
✗ ul, ol, dl                    ← قوائم
✗ table                         ← جداول
✗ figure, details               ← مكونات مركبة
✗ أي بلوك                       ← حاويات بنيوية
```

### 4.4 مثال خاطئ:

```artoon
✗ خطأ:
>.p:: هذا نص [ul:: li:عنصر]

السبب: محاولة إنشاء بنية داخل سياق لغوي
```

### 4.5 قاعدة الترتيب:

```
التوصيف دائماً قبل النوع

✓ صحيح:  [icon+img:: star.svg]
✗ خطأ:   [img+icon:: star.svg]
```

**→ راجع `10-INLINE-INTEGRATION.md` للتفاصيل الكاملة**

## 4. حدود بلوك meta

### 4.1 meta = معلومات عن المستند فقط

```
✓ مسموح:
  - عنوان المستند، الوصف، الكاتب
  - التاريخ، الإصدار، الحالة
  - التصنيف، الوسوم، اللغة
  - العلاقات مع مستندات أخرى

✗ ممنوع:
  - معلومات العرض (theme, layout, style)
  - معلومات السلوك (scripts, handlers)
  - معلومات التطبيق (api-key, config)
  - بيانات المستخدم (session, preferences)
```

### 4.2 اختبار الصلاحية:

```
السؤال: هل هذه المعلومة تصف المستند نفسه؟

✓ "من كتب هذا؟" → author ← مسموح
✓ "متى كُتب؟" → date ← مسموح
✗ "كيف يُعرض؟" → theme ← ممنوع
✗ "ماذا يفعل عند النقر؟" → onclick ← ممنوع
```

## 5. حدود البلوكات المخصصة

### 5.1 القواعد الصارمة:

```
✓ البلوك = حاوية دلالية للمحتوى
✓ الاسم يصف المحتوى وليس الشكل
✓ المحتوى الداخلي يتبع قواعد ARTOON

✗ البلوك ≠ عنصر UI
✗ البلوك ≠ تخطيط
✗ البلوك ≠ سلوك
```

### 5.2 أسماء مقبولة vs مرفوضة:

```
✓ مقبول (دلالي):
  article, post, comment, review
  chapter, section, aside, note
  quote, citation, reference
  product, event, person, place

✗ مرفوض (بصري/سلوكي):
  card, box, container, wrapper
  grid, row, column, flex
  modal, popup, slider, carousel
  button, link-button, cta
```

### 5.3 Naming Convention المقترحة:

```
البلوكات المخصصة يُفضل أن تبدأ بـ:
- x-        للتجريب
- app-      للتطبيق المحدد
- org-      للمؤسسة

مثال:
<x-experiment>.
<app-product-card>.
<org-internal-note>.
```

## 6. الأنماط المرفوضة (Anti-Patterns)

### 6.1 ✗ محاكاة HTML

```
✗ خطأ: إضافة مكون لكل عنصر HTML
✗ خطأ: نسخ attributes من HTML
✗ خطأ: التفكير بـ "كيف سيُعرض"

✓ صحيح: التفكير بـ "ما هو هذا المحتوى"
```

### 6.2 ✗ زحف الميزات (Feature Creep)

```
✗ خطأ: "لنضف X لأنه مفيد"
✗ خطأ: "المستخدمون يطلبون Y"
✗ خطأ: "HTML يدعم Z"

✓ صحيح: "هل X ضروري للمعنى الدلالي؟"
```

### 6.3 ✗ التعقيد المبرر

```
✗ خطأ: "نحتاج syntax خاص لهذه الحالة"
✗ خطأ: "لنضف modifier جديد"
✗ خطأ: "لنوسع الصيغة قليلاً"

✓ صحيح: "هل يمكن تحقيقه بالمكونات الموجودة؟"
```

### 6.4 ✗ الاستثناءات

```
✗ خطأ: "هذه حالة خاصة"
✗ خطأ: "استثناء واحد لن يضر"
✗ خطأ: "للتوافق مع X"

✓ صحيح: "القواعد تنطبق على الجميع"
```

## 7. أسئلة الفحص (Checklist)

قبل إضافة أي شيء لـ ARTOON، اسأل:

```
□ هل يصف معنى وليس شكلاً؟
□ هل هو ضروري ولا يمكن تحقيقه بالموجود؟
□ هل يتبع الصيغة الموحدة؟
□ هل يعمل مع RTL و LTR؟
□ هل يمكن تحويله لأي صيغة أخرى؟
□ هل سيبقى صالحاً بعد 10 سنوات؟
□ هل يكسر التوافق العكسي؟
□ هل يضيف تعقيداً للـ Parser؟
```

**إذا كان أي جواب "لا" أو "ربما" → لا تضفه**

## 8. لماذا نرفض طلبات شائعة

### 8.1 "أضيفوا دعم CSS inline"

```
✗ مرفوض
السبب: يكسر مبدأ فصل المحتوى عن العرض
البديل: CSS خارجي يستهدف المكونات
```

### 8.2 "أضيفوا مكون button"

```
✗ مرفوض
السبب: button = سلوك تفاعلي، وليس محتوى
البديل: >.a:: للروابط، التطبيق يحدد الشكل
```

### 8.3 "أضيفوا grid/columns"

```
✗ مرفوض
السبب: تخطيط = طبقة العرض
البديل: CSS Grid/Flexbox على البلوكات
```

### 8.4 "أضيفوا variables/templates"

```
✗ مرفوض
السبب: ARTOON ملف محتوى ثابت، وليس لغة برمجة
البديل: معالج خارجي (preprocessor)
```

### 8.5 "أضيفوا validation للـ forms"

```
✗ مرفوض
السبب: ARTOON لا تدعم forms أصلاً
البديل: تطبيق خارجي يقرأ ARTOON ويبني forms
```
